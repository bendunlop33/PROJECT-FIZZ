# 0024: Deleted workouts as a status, and the purge as a narrow trigger exception

**Status:** Proposed, 11 Oct 2026 (developer). **Needs Ben's approval before merge**: it amends ADR 0005 ("deleting data is deleting database files") for one case, purging a workout Ben deleted 30 days ago. Design: [delete-workouts.md](../design/delete-workouts.md) (DW-D1, DW-D4, §6.4, DW-Q2).

**Merge order (review B1; for the PM).** `claude/progress` also claims migration 8 (`0008-progress.ts`: `ALTER TABLE sessions ADD COLUMN duration_confirmed_at_utc / _tz`). This migration rebuilds `sessions` from a frozen column list, so it now checks `PRAGMA table_info(sessions)` first and refuses (rolling back, nothing changed) on any column it doesn't know or any it expects that is missing. Proposed order: merge `claude/progress` first; this branch then renumbers to 9 and adds its two columns to the rebuild's `CREATE TABLE`, `INSERT` lists and `SESSIONS_V7_COLUMNS` (renamed for the new base). If this branch merges first, `claude/progress` renumbers to 9 and its `ALTER`s run after the rebuild unchanged. Either way, the guard turns a forgotten step into a failed migration on a test build, never a silent loss on the phone.

## Context

Ben asked to "delete old records". The spec makes a delete a reversible status change, restorable for 30 days, then purged so only a tombstone remains. ADR 0005's append-only triggers refuse every `DELETE` of a session's rows, and ADR 0023 removes data only by rebuilding the database file. The spec recommends the ADR 0023 file rebuild for the purge (DW-Q2) and lists a narrow trigger exception as the alternative.

## Decision

1. **`deleted` is a session status** (migration 8 rebuilds `sessions` to widen the `CHECK`), with a deletion record (`deleted_at_utc/tz`, `deleted_by_op_id`, `purge_after_utc`) present exactly when the status is `deleted`. Every SQL reader that already filtered `status = 'finished'` excludes deleted workouts with no further change, and every domain reader goes through one predicate, `isInHistory` (SQL form `inHistorySql`). A source scan test fails if a new reader compares a status with `finished` directly (DW19), and a test on real SQLite runs every reader with one workout deleted and compares against a history that never had it.
2. **Delete and Restore are versioned, all-or-nothing writes** of the session aggregate: version and revision bump, the operation is recorded in `processed_operations` (`delete_workout` / `restore_workout`, with a fingerprint of the selection), so a retry with the same op ID is a duplicate and a reused op ID with a different selection is refused. No set, exercise or audit row changes.
3. **The purge deletes rows inside SQLite, under a narrow exception** instead of a file rebuild. Migration 8 adds `purged_sessions` (tombstone: ID, owner, deleted-at, purged-at, purge op, import job; no training values; append-only) and re-creates the `DELETE` triggers on `sessions`, `session_sets`, `session_exercises`, `set_audit`, `timing_audit`, `processed_operations`, `session_pauses` and `import_rows` with a `WHEN` clause: a row may go only if its session has a tombstone, and a tombstone can be written only for a session whose status is `deleted` (or that isn't stored, as when a backup is loaded). A tombstoned ID can never be inserted again. UPDATE triggers are unchanged. The purge is one transaction: a force-close leaves all of it or none (DW22).
4. **When:** at launch, after the launch backup check, when no workout is unfinished, with a daily op ID. `Delete now` purges at once.

## Why not the file rebuild

- A daily rebuild would replace the single rollback slot, so `Undo last restore` / `Undo last reset` would be lost every time a purge ran (ADR 0023 keeps one generation), and it needs the marker, resume and cover machinery for a change that touches a handful of rows.
- A transaction can't lose a set logged meanwhile, so the "never while a workout is unfinished" rule is kept only because the spec asks for it, not because it is needed.
- The exception is small and testable: tests show the database still refuses deleting a finished workout's rows, a deleted workout's rows without a tombstone, a tombstone, and re-inserting a purged ID.

## Divergences from the spec (for the PM / Ben)

- **Purge timing:** launch only (not "return to foreground"), and not limited to once a day: it is an indexed query that writes nothing when nothing is due. Foreground purge needs an AppState hook in Root; not built.
- **`Delete now` while a workout is unfinished** purges at once (one transaction), instead of marking rows purge-due for later.
- **Coach records and next-session targets of a purged workout are kept** (DW-D6 keeps conversations; targets and coach actions have their own append-only triggers). The purge removes the session's rows, its check-in, its coach offers and its import rows. **For Ben (review S7):** §6.4 says the purge removes the coach note, and the tombstone principle is "no training values", but the kept `next_session_targets` rows hold loads and reps derived from the workout and the summary turn's message keeps its numbers. Either amend §6.4 to keep them (they're never applied once the source is gone; a test reads them back after a purge), or extend the same tombstone exception to remove the source's `next_session_targets` rows and its summary note. Not built either way until Ben decides.
- **Swipe actions are not built (DW3, §2.3; §2.5 swipe `Restore`).** RN core has no swipeable row and `react-native-gesture-handler` isn't a dependency. Options: (a) add `react-native-gesture-handler` (Expo SDK 57 supported, native, needs a new dev build and a stack ADR) and use `ReanimatedSwipeable` with full-swipe off; (b) a hand-rolled `PanResponder` row (no dependency, but fights the list's scroll and needs real-device tuning). Today every row has the VoiceOver `Delete` / `Restore` action, and Select covers several. Recommend (a) as its own small slice after Ben approves the dependency.
- **`Delete set` on finished workouts, `restore_set` and the Edit history `Restore` are not built (DW30, §2.6, §3.4).** They wait on DW-Q1 (allow `delete_set` on finished workouts), which is still open; the reducer still refuses it. DW30 is conditional on DW-Q1 (spec issue SP5).
- **Memory source line `From a deleted workout` (DW16, §5)**: not built because there is no surface for it. Memories don't record the workout they came from, and no screen lists memory sources. It needs a memory list design first.
- **Voice reply `Delete workouts from Past workouts.` (DW33)**: voice (build step 5) doesn't exist yet. The coach has no delete tool (the registry refuses destructive names), and its instructions now say to decline with that line. Whether the model says exactly that is the model's wording, not a guarantee; a deterministic canned reply would conflict with rule 1.
- **Structural coach proposals (`propose_next_workout_change`) aren't built**, so DW16's "an open proposal citing it is rejected as stale on Apply" has nothing to apply. The coach write that does exist (the summary's next-session targets) is refused as stale when its source workout is deleted mid-turn (tested).
- **Restore of a backup taken before the delete (DW28, DW-Q4)**: `Keep deleted` / `Bring back` isn't built and waits on Ben's DW-Q4. The preview now says it plainly: `n workouts you deleted since this backup come back.`, with the deleted workouts counted on their own `Recently deleted` row and not as workouts replaced.
- **Copy:** `Couldn’t delete. Nothing was changed.` is banned by the minimal-copy audit (`Nothing was changed`); the app shows `Couldn’t delete.` with `Try again` (spec issue SP3). The Recently deleted footnote `Gone 30 days after deleting.` is kept as specified, though it explains a rule in the main UI (SP2: the designer may drop it and keep only `ⓘ`).
- **Import counts (SP1):** the code follows §5 (`412 workouts · 3 deleted`, the total counts every workout the import wrote), so deleting all of them reads `412 workouts · 412 deleted`, not §6.2's `0 workouts · 412 deleted`. The spec needs to pick one.
- **Coach target after an empty workout:** a routine started and finished with no set logged while its source was deleted doesn't count as "started since" (it isn't the routine's last workout), so after Restore the coach's targets apply again. Logged sets do count (tested).

## Consequences

- Backups carry deleted workouts as `deleted` with their dates and tombstones; a restored backup puts them back in Recently deleted with the original clock (past 30 days: never shown, purged at the next launch). `verifyBackup` counts them as `deletedWorkouts`, not in the workout total. Export `My data` leaves them and tombstones out. `Delete my data` removes both (they are Your data).
- Restoring a backup **taken before** the delete brings the workout back as it was in the file (DW28 / DW-Q4 `Keep deleted` isn't built).
- Device checks: migration 8 on the phone's real database (a `sessions` rebuild with foreign keys deferred, as migration 3), time of the launch purge on a large history, the toast's close button and escape gesture with VoiceOver on.
- Tombstones also keep an imported workout's local date (a date, not a training value), so an import's date view can say `This workout was deleted.` after the purge.
