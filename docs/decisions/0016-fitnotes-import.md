# 0016: FitNotes import (parser, preview, commit, Undo import)

**Status:** Proposed, 2026-10-09 (developer; for review). Built and tested on Linux only. **Not yet run on an iPhone, and not yet run against Ben's real export** (spec check 16 says to re-run detection on his file before calling this done).

## Context
Build step 3 adds FitNotes import (data-import-export.md §2.5, §3.4, §4.3, checks 16–27; brief §6–§7, scenario 6). The research (`docs/research/fitnotes-export-format.md`, fact-checked 2026-10-09) found three header families (Android ≤ v1.23, Android v24+, FitNotes 2), no time of day in any of them, per-row units in two of them, and an ambiguous Android `Time` format. Only Ben's real file can settle which one he has.

## Decision

### Where the code lives
- **Pure (`packages/domain/src/import/`):** CSV reader, header detection and row parsing (`fitnotes.ts`), name matching (`match.ts`), effort ratings in comments (`effort.ts`), the preview/answers/plan (`plan.ts`, `answers.ts`), the imported workout builder (`session.ts`) and the results CSV. Synthetic fixtures only (`test/fixtures/fitnotes/*.synthetic.csv`).
- **Storage (`packages/persistence`):** schema 3 and `SqliteImports`.
- **Orchestration (`apps/mobile/src/import/import-service.ts`)** and pure view-models (`views.ts`). Screens only render view-models and call the service.

### Formats and rows
- Exactly seven headers are recognised: A1-kg, A1-lb, A2-kg, A2-lb, B1, B2 and C (research §2). Cells are trimmed; matching is case-sensitive. Comma, semicolon and tab are tried and accepted only when the header then matches. Anything else stops with the first line shown (DX5). The unverified two-column Android header (Kinoku) is not accepted.
- A file is classified by content, never its name: SQLite magic → "FitNotes backup, not CSV"; zip or binary → "not a CSV"; `Date` without `Exercise` → Body Tracker message.
- Units are per row and never converted (A: header; B: `kgs`/`lbs`/`kg`/`lb`, any case; C: whichever column is filled). C rows with both columns filled are asked once per file. A decimal comma, a non-whole rep count, a bad or future date, or a wrong number of cells makes the row unreadable with its raw text kept; nothing is guessed.
- **Row classes:** weight and/or reps → imported. A distance with no weight or reps → cardio (skipped, P-I4). **Time only (a plank or a bike session; the columns can't tell them apart), time or distance with weight or reps, and weight with no reps → "timed, distance or weight-only sets", skipped and listed** until spec change S3 is decided. Because time is never imported, the ambiguous two-part Android `Time` is never read.
- A date after today is a planned workout in FitNotes, not one done, so it is listed as unreadable.

### Mapping (nothing pre-selected, nothing invented)
- **A suggestion gives the exercise only (PM decision, 9 Oct 2026, after review r5).** The importer never derives anything that changes the stored value of a set (one dumbbell or two, load or assistance, total or plates only, the unit) from an unconfirmed, word-similarity suggestion, even after `Use this` or `Choose…`. A load-affecting property comes only from:
  - **(a)** the FitNotes name being one of the exercise's own names (its name or a catalogue alias, ignoring case and spacing; `namesExercise`);
  - **(b)** Ben's explicit answer, in this import or remembered from an import still in effect (`Add new` with its equipment, a per-exercise or group answer, a bodyweight answer);
  - **(c)** an explicit word in the FitNotes name (`one-arm`, `single`, `two-arm`, `alternating`, `assisted`, …). **Not for the bar (PM decision after review r7):** no word in a name decides that a bar weight is added or which bar; that is only ever Ben's answer for one exercise (below).
  Anything else is asked on its own, with nothing pre-selected, and every dumbbell and barbell exercise shows what it will import as before commit. This replaces the per-name fixes of rounds 3–5 with one rule. It is enforced in `implementsFor` (dumbbell count), `totalReading` / `platesOnlyBar` (the bar: only Ben's answer for the exercise adds one; PM decision after review r7), the matcher (`kindFits`: an assisted machine only for a name that says assisted and an assisted name only an assisted or bodyweight exercise; a Smith exercise only for a Smith name and a Smith name only a Smith exercise; review r6 B2, B3), `Add new` (each equipment its own exercise, never changed by a later import; review r6 B1) and the parser (units are never converted). `fitnotes-import-defaults.test.ts` imports FitNotes' published default names (`test/fixtures/fitnotes-default-exercises.txt`) end to end in kg and in lb, accepting every `Check` and answering "Both together" and the barbell group's only answer, "Total as written", and checks every stored value against the file with its own reading of (a)–(c); it does the same for the review's Smith + Barbell and Assisted + Machine names (review r6).
- Names: `Matched` (equal to an exercise's name or catalogue name, or Ben's answer in an import still in effect), `Check` (a word-based suggestion), `No match`. Candidates are the app's exercises plus the bundled catalogue (reps-measured only). Answers are remembered as `ExerciseAlias` rows at commit.
- **Suggestions follow the name's equipment (review r4 S3).** A `Check` never suggests an exercise whose equipment contradicts an equipment word in the name (`dumbbell`/`DB`, `barbell`/`BB`, `EZ`, `trap`/`hex bar`, `kettlebell`/`KB`, `cable`/`pulley`, `machine`, `Smith`, `Hammer Strength`, `band`; `equipmentInName`). Ties are broken on equipment (the exercise whose equipment the name names wins), never by alphabetical order; a tie equipment can't break gives **no suggestion** (`Shoulder Press`, `Squat`, `Dumbbell Lunge` are now `No match` rather than whichever exercise sorted first). Two exercises with the same exact name: the one whose own name it is wins, then equipment. Against FitNotes' default names: `Flat Dumbbell Bench Press` is now the dumbbell bench press (also an alias), and `Dumbbell Skullcrusher`, `Barbell Shrug`, `Machine Shrug` and `Barbell Calf Raise` get no suggestion instead of the EZ-bar skull crusher, the dumbbell shrug and the calf-raise machine. Suggestions with the right equipment but the wrong movement remain possible (`Front Dumbbell Raise` → Lateral raise, `Seated Machine Curl` → Seated leg curl); they are `Check`s Ben confirms, and under the PM decision above they give the exercise only.
- **The FitNotes `Category` is a ranking hint only (11 Oct 2026, after the real-file run; review import-names S1, S4).** Research §3.4 says not to classify rows by it, because Ben can edit, reorder or delete categories; this stays true. The category (`categoryHint`, `muscleFit` in `packages/domain/src/import/category.ts`) only:
  - **drops** a word suggestion whose primary muscles contradict it, after the best score is taken over every fitting exercise, so it never promotes a weaker suggestion (`Romanian Deadlifts` under Back stays the Romanian deadlift; `Close Grip Bench` under Back is `No match`, never the pulldown). The row then reads `No match · <category>`;
  - **breaks a tie** between equally good suggestions, or between two exercises sharing an exact name, which stays a `Check`.
  It never makes or questions a `Matched` (an exact name or catalogue alias, or Ben's saved answer), never changes a stored value, and is never persisted (the source cell stays in `import_rows` as provenance). A blank, unknown, custom or cardio category, or a name filed under several categories one of which is unknown, gives no hint. Each category lists every primary muscle an exercise filed there may have (Back includes glutes and hamstrings, because FitNotes files deadlifts there); an exercise with no muscles recorded is never dropped. Category text is data (rule 8). Whether the hint may downgrade a catalogue-alias `Matched` to a `Check` is open for the PM (review import-names SP2).
- **Review r5 (S3, N1).** `Machine` allows a weight stack or plate-loaded machine, never an assisted machine; only `assist`/`assisted`/`Gravitron`/`counterweight` do, and an assistance exercise is never suggested for a name without one of those words (a seated dip machine's 80 kg is never 80 kg of help). A Smith machine is its own kind in the matcher: a name that says Smith is only compared with exercises whose name says Smith (`Smith Machine Overhead Press` is now `No match`, not the stack shoulder press or the Smith bench press), and a Smith exercise is never suggested for a name that doesn't say Smith. Words that only count arms (`one-arm`, `single`, `two-arm`, `alternating`, `SA`) are left out of the word comparison, so they never outweigh the movement (`Dumbbell Bench Press (Single Arm)` is the bench press, asked for its count); an exercise one of whose names says the other count is never suggested (`Two-Arm Dumbbell Row` is never the one-arm row); and a tie goes to the exercise whose own name says the same count (`Lat Pulldown (Pulley)` is the lat pulldown, not tied with the single-arm pulldown).
- **Review r6 (B2, B3, N3): Smith and assist words work both ways.** Round 5 only kept Smith and assisted exercises away from names without those words. Now also: a name that says Smith is only ever a Smith exercise, even when it says Barbell (`Smith Machine Barbell Squat` was the free back squat, and "Plates only" added the Olympic bar: 220 stored as 240 kg); and a name that says assisted is only an assisted or bodyweight exercise, even when it says Machine (`Assisted Shoulder Press Machine` was the stack shoulder press, its values stored as a load). The same rule applies to two exercises that share the exact name. A Smith name never establishes the Olympic bar (`barNamed`), so one chosen as a free-barbell exercise with `Choose…`, or added new as a barbell exercise, is asked `Total / Plates only` on its own. `Alternate grip` no longer reads as two dumbbells.
- Conventions: dumbbells (each / both) is a group question with per-exercise overrides; barbell has a group answer that can only be `Total as written` and a per-exercise `Plates only` (below); a bodyweight exercise with any non-zero weight gets its own question with the value range. Stack, plates-added and assisted-machine exercises follow the exercise.
- **One dumbbell or two (review r3 S1).** "Both dumbbells together" must never halve an exercise done with one dumbbell (a one-arm row, a goblet squat). `laterality` can't tell a one-arm row from a split squat, so per-hand catalogue entries gained an optional `implements: 1 | 2` (Coaching knowledge; `ImplementCountSchema`; the schema refuses it on anything not per-hand). Each dumbbell exercise is read (`perHandReading`) by:
  - Ben's own answer for it (`perHandOverrides`, now `one` / `each` / `both`; filled in from his answer for the same name in an earlier import, below), else
  - `one` (as written) when the catalogue says one dumbbell, whatever the group answer, else
  - the group answer (each / both) when the catalogue says two.
  - An exercise whose count isn't known (`Add new` dumbbells, a custom exercise, an entry commonly done either way, or a name that contradicts the catalogue, below) never takes the group answer; it is asked on its own (`One dumbbell / Each / Both together`), with nothing pre-selected (DX6).
  - **The count comes from the name, never from a suggestion (review r4 S1, r5 S1; `implementsFor`, `implementCue`).** Words saying one implement (`one-arm`, `single`, `one-hand`, `1 arm`, `unilateral`, `concentration`, `goblet`, `suitcase`, `SA`) or two (`two-arm`, `double`, `alternating`, `alt`; `two-hand` says neither) give the catalogue's count when they agree with it (source (c)); when they disagree, the count is unknown and asked, however the name was mapped (its words, `Use this`, `Choose…` or an earlier answer). When the name says neither, the catalogue's count, one **or two**, is inherited only when the name is one of the exercise's own names and that name doesn't owe its count to a word the source lacks (source (a)): `Dumbbell Curl` is a pair and `Dumbbell Pullover` one dumbbell; `Dumbbell Row` (an alias of the one-arm row) and `Dumbbell Squat` (suggested as the goblet squat) are asked. Since review r5 a suggested pair is asked too, so "Both together" never halves FitNotes' `Dumbbell Preacher Curl` (→ Dumbbell curl) or `Front Dumbbell Raise` (→ Lateral raise). Of FitNotes' 18 dumbbell defaults, 7 are pairs by their own names (halved by "Both together"), 3 are one dumbbell, and 8 are now asked: `Dumbbell Preacher Curl`, `Dumbbell Row`, `Front Dumbbell Raise`, `Incline Dumbbell Fly`, `Lateral Dumbbell Raise`, `Rear Delt Dumbbell Raise`, `Seated Dumbbell Lateral Raise` and `Seated Incline Dumbbell Curl` (`Walking`, suggested as the dumbbell walking lunge, is asked too). The catalogue owner can add the unambiguous ones as aliases so they match exactly.
  - **Ben's answer is remembered (review r4 S2).** His answer for an exercise (`perHandOverrides`) is saved with the name's `ExerciseAlias` (`perHand`, optional, JSON only: no migration), including for a name that matched by name and had no alias. The next preview starts with it filled in and the row says `Your answer last time`; the group question is still asked with nothing selected. Clearing it in a later import forgets it; an import that says nothing about it keeps it. The group answer itself isn't remembered (it is a group question, DX6). The remembered answers are part of the preview's staleness stamp. Only answers from imports still in effect count (Undo, below).
  - **Group question (review r5 N4):** its count (`For these 4 exercises with two dumbbells`) and example set leave out pairs that have their own answer, so the example is always one the group answer reads.
  - **Kettlebells (review r5 N3):** a kettlebell exercise on the dumbbell screen says `One kettlebell` and `24 kg → 24 kg (one kettlebell)`.
  - **Choices (review r4 N4):** a pair `Same / Each / Both together`; one dumbbell `One dumbbell / Both together` (as written or halved; `Each` gave the same result); unknown `One dumbbell / Each / Both together`. An answer these don't offer (remembered from an import that read the exercise differently) is shown, selected.
  - The dumbbell screen shows what every exercise imports as before commit (`One-Arm DB Row  30 kg → 30 kg (one dumbbell)`, `Dumbbell Bench Press  60 kg → 30 kg each`, `14 kg → not answered yet`), and the preview line counts each reading (`Dumbbells: 1 both together · 3 one dumbbell`). The catalogue count is part of the preview's staleness stamp.
  - Classification of the 33 per-hand entries: 1 (11) for one-arm row, three-point row, goblet squat, pullover, overhead triceps extension (one dumbbell, two hands), concentration curl, one-arm shoulder press, and single-arm kettlebell clean, press, snatch and get-up; 2 (17) for presses, flyes, rows on a chest support, curls, raises, shrugs, RDLs, the walking lunge, split squats and the farmer's carry; unset (5) for single-leg RDL, kettlebell front-rack carry, and (review r4 N3) the triceps kickback, step-up and reverse lunge, which are commonly done either way. Two basic entries were added for FitNotes' one-dumbbell defaults (`dumbbell-concentration-curl`, `dumbbell-one-arm-shoulder-press` with the alias `One-arm standing dumbbell press`), and `Flat dumbbell bench press` is an alias of the dumbbell bench press. **The catalogue owner should confirm these** (they were set from each entry's name, aliases and, for rich entries, setup cues).
- **Total or plates only (PM decision after review r7, 10 Oct 2026; replaces the review r5 rule and the bar-word rules of rounds 6–7).** No group answer ever adds a bar weight. The barbell group question offers only `Total as written` (`Nothing added: imported as 100 kg`; not pre-selected, DX6) and reads every bar exercise with no answer of its own. `Plates only` is chosen per exercise from a list (`Plates only (bar not counted)?`) that shows, for each, the bar it would add (`Bar: Olympic bar (from Bench press)`: the matched exercise's own bar from its equipment; Ben can change it to `Olympic bar` / `EZ bar` / `Trap bar`, then `(your choice)`), the conversion (`If plates only: 60 kg → 80 kg total (plates + 20 kg bar)`), what it imports as now (`Now: 60 kg → 60 kg total as written`), and `Total as written` / `Plates only` with nothing pre-selected. The name-based bar rules (`barNamed`, `barWordsIn`, `newBarFromName`) are removed; words in a name still help the matcher suggest which exercise it is (`equipmentInName`), never the bar. `Add new` → `Barbell` makes the exercise with the Olympic bar, or the bar Ben chose for its `Plates only` answer on this list (review r8 S2: the bar buttons appear only once `Plates only` is selected, the service refuses a bar otherwise, and any other answer drops the chosen bar; an EZ- or trap-bar exercise made this way has its own ID, `customExerciseIdFor(owner, name, 'barbell', bar)`, so an Olympic one made earlier is never changed). A group `plates_only` stored by an earlier build is read as not answered and never carried into a new preview; the service refuses a group `plates_only` answer. The preview line reads `Barbell weights: total as written, or plates only?`, `1 plates-only exercise: which bar?`, then `Barbell: 2 total as written · 1 plates only + bar`. **Remembered (exact since review r8 B1, B2):** Ben's per-exercise answer is kept on the name's alias (`uses[].total`, optional, JSON only: no migration) with the exercise it was for and, for `Plates only`, the bar it added (and whether he chose it) and that bar's weight in each unit the exercise's sets were written in (`RememberedTotal`). A later import still in effect fills it in, labelled `Your answer last time`, only when it is exactly what this import would do (`rememberedTotalFits`): the name maps to the same exercise; the bar is the one he chose, or the exercise's own bar is still the one it was read with; and the bar's weight in effect in every unit of this file's sets is the one remembered, or still empty (an EZ or trap bar's weight is then asked before anything imports). So a 15 kg-bar answer isn't filled in under the 20 kg default, a kg answer never fills in for an lb file, and an answer never follows the name to another exercise or bar (or a catalogue change of the exercise's bar). Otherwise the exercise is asked with nothing selected and shows `Last time: plates only + 15 kg Olympic bar. Not filled in: the bar or its weight is different now.` (or `…: it was for another exercise.`) as information only. Records written by the review r8 build (no exercise) are never filled in. `Undo this import` takes it back like the dumbbell answer. In one preview, re-mapping a name whose `Plates only` bar then changes clears that answer (recorded as a change, like the bodyweight answer under r6.2 N4), so the question reopens (review r8 S1). A job paused by an earlier build with a group `plates_only` is not continued: `Continue import` returns `outdated_answers` and the screen asks Ben to undo it and import the file again (review r8 S3); one whose workouts are all in is still just finished.
- **Bar weights (review S1):** the bar comes from the matched exercise's equipment (`barbell`, `ez_bar`, `trap_bar`). The Olympic bar keeps the spec's editable 20 kg / 45 lb default; EZ and trap bars have **no default** (they vary), so their plates-only rows wait (the question stays open) until Ben enters that bar's weight. `total` exercises with no bar (kettlebell, medicine ball, sandbag) aren't in the barbell question: imported as written and listed under "Kept as written". An exercise with no single bar recorded shows `Choose one for plates only`: its plates-only rows wait until Ben chooses a bar (`needsBar`), never unreadable and never the Olympic bar by default.
- **Bodyweight answers (review B3):** `Weight added` / `Assistance` / and, only when the exercise's values span zero, `Negative = assistance, positive = added`. Under `Assistance`, a positive value in a file that also has negative values for that exercise is unreadable, never flipped into assistance; a one-way file (all positive machine numbers, or all negative) is read as assistance. Same-day assisted and weighted sets become two exercise entries (one convention each).
- **Negative weights (provisional, Ben to confirm):** read as that much assistance only where the convention is assistance (Ben's bodyweight answer, or an assisted-machine exercise). Anywhere else the row is unreadable.
- Loads are imported as written: never snapped to equipment (rule 2), never converted.
- RPE is set only on rows Ben ticked after choosing `Review and import as RPE`.

### Imported workouts
- One workout per date (FitNotes keeps one per calendar date), `finished`, `source: 'import'`, linked to its job, **date-only** (`localDate`). `startedAt` is only an ordering anchor at 12:00 local on that date in the phone's zone at import; there is no end time, and timing edits are refused for these workouts.
- **Date-only everywhere it shows (review B2, N3):** `dateOnlyOf(session)` / `workoutDurationMs` (null for date-only). Today matches it by its own date (not the anchor in the phone's current zone) and says `Workout done` with no duration; Summary shows `<date> · date only` with no time range, no Active time and no `Edit times`. Past workouts already show the date only.
- No equipment instance is attached (the file doesn't say which machine or bar). **Superseded 12 Oct 2026 by the B7 amendment below (P-I3 option (b)).** Until then, option (a) was enforced explicitly, not through `equipmentId` (review r2 B1). Matching on equipment alone let imported history through wherever neither side had equipment (an exercise added with no equipment because the gym has none of that kind), and let an imported workout be repeated with loads no equipment had checked:
  - `HistorySession` carries `imported` and `gymId`. Imported history is skipped by `lastComparableSession` ("Last" and prefill), the built-in rule's `comparableSessions` (targets, `Next time`, planned sets on Add exercise) and `summaryHighlight`.
  - **Imported workouts aren't repeatable.** `listRepeatableIds` and `repeat.candidates` leave them out (`Repeat last workout` is the newest workout logged in the app), and `startFromSession` refuses one (`imported_not_repeatable`), so a stale link can't plan one either. `Start from a past workout` says how many were left out and where they are (Data & backup → Past imports).
  - The Summary of an imported workout has no comparison, highlight or `Next time` (it's a history record). A workout logged in the app whose only earlier sets of an exercise came from FitNotes says `Earlier Lat pulldown sets were imported from FitNotes. Not compared.` rather than "First time".
  - The comparison's `why` names the compared workout's own gym (`Same set-up at Home`), `, gym not recorded`, or no gym when its name isn't known; never today's gym by assumption.
  - P-I3 (open-decisions B7) must now also decide whether imported workouts can be repeated, and how a load from `Gym: Not recorded` is checked at the current gym (pick equipment, round toward easier, never above a max; or drop the load with a note).
- Every set is a working set (FitNotes has no warm-up flag; research S6). Unilateral sets are `both` (the logger's default). The rest snapshot is `0 s`, source `not_recorded` (`Not recorded (imported)`; a set-only rest source that never reaches a rest timer, review N6). Each set gets one `logged` audit entry stamped with the commit time.
- Comments are kept with each row as the original (provenance). There is no set-notes field yet, so "kept as notes" means kept and shown as the original comment.

### Amendment, 12 Oct 2026: P-I3 decided as option (b) (B7)
Ben accepted B7 on 11 Oct 2026 (CHANGELOG "Backlog defaults accepted": FitNotes history shown as `Last (FitNotes, date)` and repeatable). It was not built until Ben reported, on build 131, that imported data didn't show up in progressions. The option (a) rules above are replaced:
- **Comparable history.** Imported history matches on exercise, unit and load convention, on any equipment (`matchesEquipment`). Readers: `lastComparableSession` (Last and prefill), the built-in rule's `comparableSessions`, the overview's LAST/BEST and change markers, the Summary comparison (`why: FitNotes, working sets`) and highlight, `Why?` (basis recorded with `imported: true`, shown as `1 Oct · FitNotes`), the pain sheet's Before/Since, substitute targets and ranking, and Today's lift highlight. Wherever it shows it is labelled FitNotes.
- **Working sets of an imported workout (`comparableSetsOf`).** FitNotes has no warm-up flag, so a ramp arrives as working sets. Comparisons and targets leave out only the lighter sets **before** the workout's hardest set (per unit and convention): a leading ramp. The hardest set and every set after it are kept, so back-off sets and descending pyramids count (review import-progress B2: 38% of Ben's real exercise-sessions have lighter sets after the top set; the first reading, "only the sets at the hardest load", read them as warm-ups). Stored sets are unchanged, and the coach's history tools still see every set. **Provisional: reading (a) of the review's options (a) leading ramp only, (b) the load with the most sets, (c) every set as stored. Ben to confirm before it is recorded in the CHANGELOG.**
- **Set count from an imported workout (`importedWorkingSetCount`, review B1).** Start next, Up next and Add exercise plan as many working sets as the same reading keeps, never fewer than the built-in default (3) because of the reading, and never more than the workout had. A ramp to one top set plans 3, not 1 and not every set at the top load; a 2-set workout plans 2.
- **Rule 4.** Targets from FitNotes go through the same equipment checks as any target: the rule rounds toward easier on today's item and never goes above its max. With no equipment here to check a FitNotes load on, the rule prescribes no load (`Pick a load…`). The one exception is `fitLater`: Start next from an imported workout, where `snapPlanToGym` fits the loads afterwards.
- **Repeatable.** `startFromSession` no longer refuses imported workouts. Each exercise is pinned to an item that exists nowhere (`importPinId`), so the shared fit maps one at this gym by the exercise's kinds (last used here, then same kind, then another kind). It rounds toward easier and never goes above a max, or drops the load when nothing here fits. `listRepeatableIds`, `listPastWorkoutIds`, Repeat candidates, Up next's fallback and `resolveNext` include imported workouts. Past workouts lists them with the `Imported` tag (DW-Q3).
- **Session picker.** Decision 1 is on (`groupImportsByCategory`): Category cells are read from `import_rows` (`categoriesBySession`), and every type is startable. Decision 2 (longest-gap Up next) is wired into the shared Up next resolver (review import-progress S1): when the D19 rotation doesn't apply, Up next starts from the history type with the longest gap (`longestGapSource`), never the workout just done (often the newest FitNotes one). Its basis line is still D19's `From <date>`; §2.3's `UP NEXT · LAST DONE` copy is not built.
- **Unchanged.** Records on Progress (PG30) and the in-workout set record are still judged only on workouts logged in the app; imported sets only suppress a claim. Imported workouts still have no Summary comparison or `Next time` of their own. The rotation and pace (`listFinishedRefs`) still read app workouts only; `includeImported` is for "the last workout Ben did" (the pain chips from Today, Decision 2's just-done type).

### Storage (schema 3)
- `import_jobs` (document; status `committing` / `committed` / `reverted`; one `committing` per owner), `import_rows` (every source row with raw cells, result, detail and the set it became; triggers forbid UPDATE and DELETE), `exercise_aliases` (owner-scoped: Ben's naming is Your data, rule 10).
- **`sessions` is rebuilt** because SQLite can't change a CHECK or NOT NULL in place: `status` gains `reverted`; `gym_id` may be NULL for imported workouts only (Gym: Not recorded); `import_job_id` and `local_date` are added. The rebuild copies, drops and re-creates the table inside the migration's transaction with foreign keys deferred; re-inserting the rows under the same name resolves the children's references before commit. Tested from schema 2 with data and with foreign keys enforced (node:sqlite), and through the existing schema-1 backup restore.
- Integrity checks validate import jobs, aliases and every import row. Backups carry everything (they copy every table). Restore analysis ignores reverted workouts like discarded ones and counts import jobs and aliases as Your data.

### Commit, resume and undo
- The preview lives in memory; nothing is saved until commit. Every answer bumps `mappingVersion`; a stale answer or commit is refused. At commit the data the preview was checked against (exercise list, remembered names, dates in the app, earlier imports) is re-read; if it changed, the preview is rebuilt and Ben confirms again (rule 5).
- Refused while a workout is unfinished (DX4) and while another import is unfinished. Backs up on this phone first (reason `before_import`; a failure stops the import) and after (`after_import`). The commit-time staleness check also covers the profile's unit, the gym list and each exercise's equipment (review N9).
- One transaction writes the job, every source row, new custom exercises (`Add new`, deterministic ID per owner, name and equipment; an exercise already stored is never changed), catalogue exercises the rows use that aren't stored yet (same catalogue IDs), and the remembered names. Then one transaction per workout, oldest first, each idempotent by its start operation (`<operationId>:<date>`) with deterministic session, exercise and set IDs. `Stop` and a force-close leave whole workouts only; `Continue import` (or the same commit retried) finishes with exactly the planned workouts.
- **Unfinished means `committing`, whatever the count (review B1).** Only `committed` is shown as finished. A `committing` import not being written by this app run is `paused` and offers `Continue import`, including one whose workouts are all in (closed or failed right before it was marked finished: `Import not finished. All 412 workouts are in your history; Continue import finishes it.`). The next read of past imports, the paused import or the same file finishes such an import (with its `after_import` backup); a failure leaves it paused. A failed final step is reported (`finish_failed`), never shown as finished.
- **One write loop per import (review N2):** a second `Import` tap joins the commit in flight; `Continue import` while it runs joins the same loop; Undo is refused (`busy`) until it ends.
- Same file (SHA-256 of the text, any name) with an import still in effect: if that import is unfinished, it says where it stopped and points to it instead (review N1). If it's finished, "Nothing new to import" is said **only while it's true (review r3 S2)**: the file is analysed again with the answers Ben gave that import, against what is in the app now, and only when that brings nothing in. Otherwise (an older import it relied on was undone, or a workout logged in the app on one of its dates is gone) the normal preview opens with `You imported this file on Thu 8 Oct. Workouts from it that are still in GymSmarter are skipped; dates that aren’t in GymSmarter now are offered again, with your answers from then filled in.` It starts from that import's answers (review r4 N2: the dates it brings back are read like the ones it brought in), except names (remembered as aliases) and a gym that no longer exists; remembered dumbbell answers win over them (`startingAnswers`). Dates that came in with an import still in effect (committing or committed) are always skipped, so a newer export never overwrites a set corrected in the app. Dates with a workout logged in the app are skipped by default (question).
- `Undo this import`: versioned and idempotent per operation; the job's workouts become `reverted` (version and storage revision bump, so a stale copy can't be saved over them) and nothing is deleted (DX7). Refused while the import is being written and while a workout is unfinished. The file can then be imported again.
- **Undo takes back what the import taught (review r5 S2, decided by the PM).** Each `ExerciseAlias` keeps one `use` per import that answered or used the name (`uses`: the exercise or Skip, and the dumbbell answer when that import asked; at most 100, oldest dropped; optional, so older records read as one use by their `jobId`). Nothing is rolled back in storage: the preview's context ignores the uses of reverted imports (`rememberedAnswers`), so a name and its dumbbell answer come from the newest import still in effect, or, with none, are matched or asked again with nothing selected (DX6). An import that used a remembered name records it again, so the name stays in effect with that import even if the import that taught it is undone. The custom exercise an `Add new` made (`customExerciseIdFor`) is kept but is never `Matched` by its name (`importMade`, `isImportMadeExercise`): it is reached through the remembered answer while that import is in effect, or suggested as a `Check`, whose count and bar are then asked.
- **An import never changes an exercise (review r6 B1).** Round 5 let `Add new` with other equipment rewrite the custom exercise made for the name, and Undo import didn't restore it: after two undos, a name an import still in effect read as a weight stack was stored as assistance with no question. Now each `Add new` equipment has its own exercise (`customExerciseIdFor(owner, name, equipment)`), and committing only ever inserts exercises. Undo then needs nothing more: the remembered name falls back to the import still in effect, which points at an exercise that never changed. An exercise an earlier build made under the old one-per-name ID is still recognised as import-made, and `Add new` reuses it only when it is exactly that equipment. Two custom exercises can share a FitNotes name (`Pull Up Machine`, weight stack; `Pull Up Machine`, assisted machine); `Choose…` shows each one's equipment.
- **A preview rebuilt because the data changed (review r6 S1)** starts again from Ben's answers in effect then (`startingAnswers`: this file's finished import and each name's dumbbell answer from imports not undone) and replays only the answers he gave in that preview, so a dumbbell answer filled in from an import undone in the meantime is never kept.
