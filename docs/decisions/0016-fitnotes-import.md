# 0016: FitNotes import (parser, preview, commit, Undo import)

**Status:** Proposed, 2026-10-09 (developer; for review). Built and tested on Linux only. **Not yet run on an iPhone, and not yet run against Ben's real export** (spec check 16 says to re-run detection on his file before calling this done).

## Context
Build step 3 adds FitNotes import (data-import-export.md §2.5, §3.4, §4.3, checks 16–27; brief §6–§7, scenario 6). The research (`docs/research/fitnotes-export-format.md`, fact-checked 2026-10-09) found three header families (Android ≤ v1.23, Android v24+, FitNotes 2), no time of day in any of them, per-row units in two of them, and an ambiguous Android `Time` format. Only Ben's real file can settle which one he has.

## Decision

### Where the code lives
- **Pure (`packages/domain/src/import/`):** CSV reader, header detection and row parsing (`fitnotes.ts`), name matching (`match.ts`), effort ratings in comments (`effort.ts`), the preview/answers/plan (`plan.ts`, `answers.ts`), the imported workout builder (`session.ts`) and the results CSV. Synthetic fixtures only (`test/fixtures/fitnotes/*.synthetic.csv`).
- **Storage (`packages/persistence`):** schema 3 and `SqliteImports`.
- **Orchestration (`apps/mobile/src/import/import-service.ts`)** and pure view-models (`views.ts`). Screens only render view-models and call the service.

### Formats and rows
- Exactly seven headers are recognised: A1-kg, A1-lb, A2-kg, A2-lb, B1, B2 and C (research §2). Cells are trimmed; matching is case-sensitive. Comma, semicolon and tab are tried and accepted only when the header then matches. Anything else stops with the first line shown (DX5). The unverified two-column Android header (Kinoku) is not accepted.
- A file is classified by content, never its name: SQLite magic → "FitNotes backup, not CSV"; zip or binary → "not a CSV"; `Date` without `Exercise` → Body Tracker message.
- Units are per row and never converted (A: header; B: `kgs`/`lbs`/`kg`/`lb`, any case; C: whichever column is filled). C rows with both columns filled are asked once per file. A decimal comma, a non-whole rep count, a bad or future date, or a wrong number of cells makes the row unreadable with its raw text kept; nothing is guessed.
- **Row classes:** weight and/or reps → imported. A distance with no weight or reps → cardio (skipped, P-I4). **Time only (a plank or a bike session; the columns can't tell them apart), time or distance with weight or reps, and weight with no reps → "timed, distance or weight-only sets", skipped and listed** until spec change S3 is decided. Because time is never imported, the ambiguous two-part Android `Time` is never read.
- A date after today is a planned workout in FitNotes, not one done, so it is listed as unreadable.

### Mapping (nothing pre-selected, nothing invented)
- Names: `Matched` (equal to an exercise's name or catalogue name, or Ben's earlier answer), `Check` (a word-based suggestion), `No match`. Candidates are the app's exercises plus the bundled catalogue (reps-measured only). Answers are remembered as `ExerciseAlias` rows at commit.
- **Suggestions follow the name's equipment (review r4 S3).** A `Check` never suggests an exercise whose equipment contradicts an equipment word in the name (`dumbbell`/`DB`, `barbell`/`BB`, `EZ`, `trap`/`hex bar`, `kettlebell`/`KB`, `cable`/`pulley`, `machine`, `Smith`, `Hammer Strength`, `band`; `equipmentInName`). Ties are broken on equipment (the exercise whose equipment the name names wins), never by alphabetical order; a tie equipment can't break gives **no suggestion** (`Shoulder Press`, `Squat`, `Dumbbell Lunge` are now `No match` rather than whichever exercise sorted first). Two exercises with the same exact name: the one whose own name it is wins, then equipment. Against FitNotes' default names: `Flat Dumbbell Bench Press` is now the dumbbell bench press (also an alias), and `Dumbbell Skullcrusher`, `Barbell Shrug`, `Machine Shrug` and `Barbell Calf Raise` get no suggestion instead of the EZ-bar skull crusher, the dumbbell shrug and the calf-raise machine. Suggestions with the right equipment but the wrong movement remain possible (`Front Dumbbell Raise` → Lateral raise, `Seated Machine Curl` → Seated leg curl); they are `Check`s Ben confirms.
- Conventions: dumbbells (each / both) and barbell (total / plates only) are group questions with per-exercise overrides; a bodyweight exercise with any non-zero weight gets its own question with the value range. Stack, plates-added and assisted-machine exercises follow the exercise.
- **One dumbbell or two (review r3 S1).** "Both dumbbells together" must never halve an exercise done with one dumbbell (a one-arm row, a goblet squat). `laterality` can't tell a one-arm row from a split squat, so per-hand catalogue entries gained an optional `implements: 1 | 2` (Coaching knowledge; `ImplementCountSchema`; the schema refuses it on anything not per-hand). Each dumbbell exercise is read (`perHandReading`) by:
  - Ben's own answer for it (`perHandOverrides`, now `one` / `each` / `both`; filled in from his answer for the same name in an earlier import, below), else
  - `one` (as written) when the catalogue says one dumbbell, whatever the group answer, else
  - the group answer (each / both) when the catalogue says two.
  - An exercise whose count isn't known (`Add new` dumbbells, a custom exercise, an entry commonly done either way, or a name that contradicts the catalogue, below) never takes the group answer; it is asked on its own (`One dumbbell / Each / Both together`), with nothing pre-selected (DX6).
  - **The source name can overrule the catalogue's count (review r4 S1; `implementsFor`, `implementCue`).** Words saying one implement (`one-arm`, `single`, `one-hand`, `1 arm`, `unilateral`, `concentration`, `goblet`, `suitcase`, `SA`) or two (`two-arm`, `double`, `alternating`, `alt`; `two-hand` says neither). When the name's word disagrees with the catalogue, the count is unknown and asked, however the name was mapped (its words, `Use this`, `Choose…` or an earlier answer): `One-Arm Standing Dumbbell Press` mapped to the two-dumbbell standing press is never halved by "Both together". When the name says neither, a pair stays a pair, but one dumbbell is inherited only when the name is the catalogue's own name for the exercise and that name doesn't owe its "one" to a word the source lacks: `Dumbbell Pullover` reads as one dumbbell; `Dumbbell Row` (an alias of the one-arm row; some people mean a two-dumbbell row, r4 N3) and `Dumbbell Squat` (suggested as the goblet squat) are asked.
  - **Ben's answer is remembered (review r4 S2).** His answer for an exercise (`perHandOverrides`) is saved with the name's `ExerciseAlias` (`perHand`, optional, JSON only: no migration), including for a name that matched by name and had no alias. The next preview starts with it filled in and the row says `Your answer last time`; the group question is still asked with nothing selected. Clearing it in a later import forgets it; an import that says nothing about it keeps it. The group answer itself isn't remembered (it is a group question, DX6). The remembered answers are part of the preview's staleness stamp.
  - **Choices (review r4 N4):** a pair `Same / Each / Both together`; one dumbbell `One dumbbell / Both together` (as written or halved; `Each` gave the same result); unknown `One dumbbell / Each / Both together`. An answer these don't offer (remembered from an import that read the exercise differently) is shown, selected.
  - The dumbbell screen shows what every exercise imports as before commit (`One-Arm DB Row  30 kg → 30 kg (one dumbbell)`, `Dumbbell Bench Press  60 kg → 30 kg each`, `14 kg → not answered yet`), and the preview line counts each reading (`Dumbbells: 1 both together · 3 one dumbbell`). The catalogue count is part of the preview's staleness stamp.
  - Classification of the 33 per-hand entries: 1 (11) for one-arm row, three-point row, goblet squat, pullover, overhead triceps extension (one dumbbell, two hands), concentration curl, one-arm shoulder press, and single-arm kettlebell clean, press, snatch and get-up; 2 (17) for presses, flyes, rows on a chest support, curls, raises, shrugs, RDLs, the walking lunge, split squats and the farmer's carry; unset (5) for single-leg RDL, kettlebell front-rack carry, and (review r4 N3) the triceps kickback, step-up and reverse lunge, which are commonly done either way. Two basic entries were added for FitNotes' one-dumbbell defaults (`dumbbell-concentration-curl`, `dumbbell-one-arm-shoulder-press` with the alias `One-arm standing dumbbell press`), and `Flat dumbbell bench press` is an alias of the dumbbell bench press. **The catalogue owner should confirm these** (they were set from each entry's name, aliases and, for rich entries, setup cues).
- **Bar weights (review S1):** the bar comes from the matched exercise's equipment (`barbell`, `ez_bar`, `trap_bar`). The Olympic bar keeps the spec's editable 20 kg / 45 lb default; EZ and trap bars have **no default** (they vary), so their plates-only rows wait (the question stays open) until Ben enters that bar's weight. `total` exercises with no bar (kettlebell, medicine ball, sandbag) aren't in the barbell question: imported as written and listed under "Kept as written". An exercise with no single bar recorded can't have a bar added: its plates-only rows are unreadable.
- **Bodyweight answers (review B3):** `Weight added` / `Assistance` / and, only when the exercise's values span zero, `Negative = assistance, positive = added`. Under `Assistance`, a positive value in a file that also has negative values for that exercise is unreadable, never flipped into assistance; a one-way file (all positive machine numbers, or all negative) is read as assistance. Same-day assisted and weighted sets become two exercise entries (one convention each).
- **Negative weights (provisional, Ben to confirm):** read as that much assistance only where the convention is assistance (Ben's bodyweight answer, or an assisted-machine exercise). Anywhere else the row is unreadable.
- Loads are imported as written: never snapped to equipment (rule 2), never converted.
- RPE is set only on rows Ben ticked after choosing `Review and import as RPE`.

### Imported workouts
- One workout per date (FitNotes keeps one per calendar date), `finished`, `source: 'import'`, linked to its job, **date-only** (`localDate`). `startedAt` is only an ordering anchor at 12:00 local on that date in the phone's zone at import; there is no end time, and timing edits are refused for these workouts.
- **Date-only everywhere it shows (review B2, N3):** `dateOnlyOf(session)` / `workoutDurationMs` (null for date-only). Today matches it by its own date (not the anchor in the phone's current zone) and says `Workout done` with no duration; Summary shows `<date> · date only` with no time range, no Active time and no `Edit times`. Past workouts already show the date only.
- No equipment instance is attached (the file doesn't say which machine or bar). **P-I3 stays open; until it's decided, option (a) is enforced explicitly, not through `equipmentId` (review r2 B1).** Matching on equipment alone let imported history through wherever neither side had equipment (an exercise added with no equipment because the gym has none of that kind), and let an imported workout be repeated with loads no equipment had checked:
  - `HistorySession` carries `imported` and `gymId`. Imported history is skipped by `lastComparableSession` ("Last" and prefill), the built-in rule's `comparableSessions` (targets, `Next time`, planned sets on Add exercise) and `summaryHighlight`.
  - **Imported workouts aren't repeatable.** `listRepeatableIds` and `repeat.candidates` leave them out (`Repeat last workout` is the newest workout logged in the app), and `startFromSession` refuses one (`imported_not_repeatable`), so a stale link can't plan one either. `Start from a past workout` says how many were left out and where they are (Data & backup → Past imports).
  - The Summary of an imported workout has no comparison, highlight or `Next time` (it's a history record). A workout logged in the app whose only earlier sets of an exercise came from FitNotes says `Earlier Lat pulldown sets were imported from FitNotes. Not compared.` rather than "First time".
  - The comparison's `why` names the compared workout's own gym (`Same set-up at Home`), `, gym not recorded`, or no gym when its name isn't known; never today's gym by assumption.
  - P-I3 (open-decisions B7) must now also decide whether imported workouts can be repeated, and how a load from `Gym: Not recorded` is checked at the current gym (pick equipment, round toward easier, never above a max; or drop the load with a note).
- Every set is a working set (FitNotes has no warm-up flag; research S6). Unilateral sets are `both` (the logger's default). The rest snapshot is `0 s`, source `not_recorded` (`Not recorded (imported)`; a set-only rest source that never reaches a rest timer, review N6). Each set gets one `logged` audit entry stamped with the commit time.
- Comments are kept with each row as the original (provenance). There is no set-notes field yet, so "kept as notes" means kept and shown as the original comment.

### Storage (schema 3)
- `import_jobs` (document; status `committing` / `committed` / `reverted`; one `committing` per owner), `import_rows` (every source row with raw cells, result, detail and the set it became; triggers forbid UPDATE and DELETE), `exercise_aliases` (owner-scoped: Ben's naming is Your data, rule 10).
- **`sessions` is rebuilt** because SQLite can't change a CHECK or NOT NULL in place: `status` gains `reverted`; `gym_id` may be NULL for imported workouts only (Gym: Not recorded); `import_job_id` and `local_date` are added. The rebuild copies, drops and re-creates the table inside the migration's transaction with foreign keys deferred; re-inserting the rows under the same name resolves the children's references before commit. Tested from schema 2 with data and with foreign keys enforced (node:sqlite), and through the existing schema-1 backup restore.
- Integrity checks validate import jobs, aliases and every import row. Backups carry everything (they copy every table). Restore analysis ignores reverted workouts like discarded ones and counts import jobs and aliases as Your data.

### Commit, resume and undo
- The preview lives in memory; nothing is saved until commit. Every answer bumps `mappingVersion`; a stale answer or commit is refused. At commit the data the preview was checked against (exercise list, remembered names, dates in the app, earlier imports) is re-read; if it changed, the preview is rebuilt and Ben confirms again (rule 5).
- Refused while a workout is unfinished (DX4) and while another import is unfinished. Backs up on this phone first (reason `before_import`; a failure stops the import) and after (`after_import`). The commit-time staleness check also covers the profile's unit, the gym list and each exercise's equipment (review N9).
- One transaction writes the job, every source row, new custom exercises (`Add new`, deterministic ID per owner and name), catalogue exercises the rows use that aren't stored yet (same catalogue IDs), and the remembered names. Then one transaction per workout, oldest first, each idempotent by its start operation (`<operationId>:<date>`) with deterministic session, exercise and set IDs. `Stop` and a force-close leave whole workouts only; `Continue import` (or the same commit retried) finishes with exactly the planned workouts.
- **Unfinished means `committing`, whatever the count (review B1).** Only `committed` is shown as finished. A `committing` import not being written by this app run is `paused` and offers `Continue import`, including one whose workouts are all in (closed or failed right before it was marked finished: `Import not finished. All 412 workouts are in your history; Continue import finishes it.`). The next read of past imports, the paused import or the same file finishes such an import (with its `after_import` backup); a failure leaves it paused. A failed final step is reported (`finish_failed`), never shown as finished.
- **One write loop per import (review N2):** a second `Import` tap joins the commit in flight; `Continue import` while it runs joins the same loop; Undo is refused (`busy`) until it ends.
- Same file (SHA-256 of the text, any name) with an import still in effect: if that import is unfinished, it says where it stopped and points to it instead (review N1). If it's finished, "Nothing new to import" is said **only while it's true (review r3 S2)**: the file is analysed again with the answers Ben gave that import, against what is in the app now, and only when that brings nothing in. Otherwise (an older import it relied on was undone, or a workout logged in the app on one of its dates is gone) the normal preview opens with `You imported this file on Thu 8 Oct. Workouts from it that are still in GymSmarter are skipped; dates that aren’t in GymSmarter now are offered again, with your answers from then filled in.` It starts from that import's answers (review r4 N2: the dates it brings back are read like the ones it brought in), except names (remembered as aliases) and a gym that no longer exists; remembered dumbbell answers win over them (`startingAnswers`). Dates that came in with an import still in effect (committing or committed) are always skipped, so a newer export never overwrites a set corrected in the app. Dates with a workout logged in the app are skipped by default (question).
- `Undo this import`: versioned and idempotent per operation; the job's workouts become `reverted` (version and storage revision bump, so a stale copy can't be saved over them) and nothing is deleted (DX7). Refused while the import is being written and while a workout is unfinished. Remembered names and custom exercises are kept. The file can then be imported again.

## Differences from the spec (for the designer / PM)
1. **Extra skip category** `timed, distance or weight-only sets` and results code `skipped_unsupported` (research S3). Time-only rows aren't called cardio.
2. **`Undo this import` is also blocked by an unfinished workout** (DX4's reasoning applies: it reshapes the history the workout reads). The spec only says this for restore and import.
3. **`Copy first line` is `Share first line`** (the iOS share sheet has Copy), plus selectable text. The app has no clipboard module; adding one is a native dependency and a new build.
4. **No row-count progress while reading** (`Reading file… 2,000 of 4,212 rows`): parsing is synchronous and fast on Linux (below); the button reads `Reading file…`.
5. **Row-by-row results CSV is saved through the folder picker** (like `Save a copy to Files`, ADR 0009) and read back before it says saved, instead of the share sheet.
6. **"Kept as notes"** is the original comment kept with each row (no set-notes field exists).
7. **Provenance** (`Imported from FitNotes on … · row …` / `Original: …`) is shown after the import on the results screen: `Imported workouts (n)` lists each date, and each opens its sets with the file, row and original values (check 24; review S2). It's also available as `imports.provenance(setId)`. There is no history set-detail screen yet; when one exists it should show the same two lines.
8. Not built: the onboarding Ready screen's `Import FitNotes history` link, export, delete.
9. Copy says GymSmarter, not Fizz.
10. **Bodyweight question has a third answer** for mixed-sign values (`Negative = assistance, positive = added`), shown only when values span zero (review B3; spec issue SP5). Copy to confirm with the designer.
11. **Bar weight per bar kind** (Olympic / EZ / trap; EZ and trap have no default), and no-bar `total` exercises (kettlebell) aren't asked (review S1; spec issue SP4). The spec has one `Bar weight` for the group.
12. **Date-only rules on Today and Summary** as above (review B2; spec issue SP6: the spec only says FitNotes workouts "show the date only").
13. Extra copy: `Import not finished. All n workouts are in your history; Continue import finishes it.`; the same file while its import is unfinished: `You started importing this file on Thu 8 Oct. Import paused at x of y workouts. … Continue that import instead.`; a failed final step: `n workouts are in, but the import couldn't be marked finished: <reason>. Try again to finish it.`
14. The preview can't be swiped away (its back is `Cancel`, which confirms); leaving it any way drops the draft (review N8).
15. **Imported workouts aren't in `Start from a past workout` or `Repeat last workout`** (review r2 B1). New copy: `412 workouts imported from FitNotes aren’t listed: imported workouts can’t be repeated yet. They’re in Data & backup, under Past imports.`; with none logged in the app, `No workouts logged in the app yet.`
16. **Summary wording** (review r2 B1): `Earlier <exercise> sets were imported from FitNotes. Not compared.`; the comparison names the compared workout's gym (`Same set-up at Home, working sets`, `…, gym not recorded, …`); an imported workout's Summary has no comparison, highlight or `Next time`.
17. **The gym question's footnote** now says what happens: `Imported sets aren’t linked to a particular machine or bar. For now they’re kept and listed under Data & backup → Past imports, but aren’t used as “Last” values or targets, and imported workouts can’t be repeated.` (review r3 N3: there's no history list for them yet).
18. **Bar weight field** (review r2 S1, r3 N1–N2): while cleared or unreadable it says `Enter a bar weight above 0. Until you do, 20 kg is added to plates-only values.`; above 100 kg / 220 lb, `Enter a bar weight up to 100 kg. …` and nothing is saved; when editing ends it shows the stored weight again. An EZ or trap bar (no default) keeps its `Enter your EZ bar’s weight…` message.
19. Smaller copy (review r2 N1–N5): the same unfinished file says `Continue` once, and a running import says `It’s importing now: 2 of 5 workouts in.`; the Data & backup row uses the same paused line as the import screens; an imported set reads `Lat pulldown · imported as 45 kg stack × 10` (a later correction in the app isn't shown there); a workout whose save wasn't confirmed reads `Workout 2 (…) may not have saved: <reason>. 1 workout is in before it. Each workout saves whole or not at all; Try again checks and carries on.`; a chosen `Negative = assistance, positive = added` answer stays visible after the values stop spanning zero.
20. **Dumbbell screen (review r3 S1; spec issue SP2).** The spec treats every per-hand exercise as a pair. Now: the group question names only two-dumbbell exercises (`For these 7 exercises with two dumbbells, “60” means:`) and is hidden when there are none; a `One dumbbell or two?` section asks for exercises with no recorded count (`GymSmarter doesn’t know whether this exercise uses one dumbbell or two. Choose for each.`); the `Different for some?` list (`Each exercise` with no group question) shows every other exercise's conversion, with `n exercises use one dumbbell, so their weights are imported as written.` Choices: `Same / Each / Both together` for a pair, `One dumbbell / Each / Both together` otherwise. The preview line can read `n dumbbell exercises: one dumbbell or two?`. Copy for the designer to confirm.
21. **Same file after an undo (review r3 S2; spec issue SP3).** §3.4's "Same file again" assumed the file's import still covers it. The preview above, with its notice line, replaces "Nothing new to import" when it doesn't. Since review r4 (N2) it starts from that import's answers, and the notice says so.
22. **Remembered dumbbell answers (review r4 S2; r4 spec issue SP2).** §2.5 step 3a remembers names; step 3b is silent and DX6 forbids pre-selected answers. Ben's own earlier answer for an exercise is treated as his data, not a default: filled in and labelled `Your answer last time` under the exercise's conversion. Copy for the designer.
23. **What a `Check` may suggest (review r4 S3; r4 spec issue SP3).** Never an exercise whose equipment contradicts an equipment word in the name; ties broken on equipment; an unbreakable tie suggests nothing. §2.5 only says "a suggestion based on the name only".
24. **One-dumbbell choices are `One dumbbell / Both together`** (review r4 N4), and a name whose words disagree with the catalogue's count is asked under `One dumbbell or two?` with the same lead as any unknown exercise (no extra copy saying why).

## Consequences
- Measured on Linux (V8) for a synthetic 10,000-row file: parse 74 ms, preview 137 ms, re-preview after an answer ~94 ms, freezing the rows ~250 ms. Hermes will be several times slower; check 27 (summary within 5 s on the iPhone) still needs measuring on the phone.
- **Device checks needed:** migration 3 under expo-sqlite (the sessions rebuild) on a phone with real workouts, after a backup to Files; the CSV document picker (`text/csv`, `text/plain`) from iCloud Drive, On My iPhone and a file saved from FitNotes 2's email export; Stop / force-close / Continue; Undo; 10,000-row timings.
- No new dependency and no new native code; the next cloud build only needs the JS.
- **Still open after review round 2:** same-day assisted and weighted entries of one exercise (the `split` answer) both read `Pull-up` in Summary (r2 N6; a label such as `Pull-up (assisted)` needs the designer); a Smith machine or any bar other than Olympic, EZ and trap can't get its own bar weight (r2 N7, SP3); `job()` decodes every row on each results-screen focus and needs timing on the phone with check 27 (r2 N8).
- **Still open after review fixes:** the week count on Today still uses the anchor (a date-only workout in a zone 12+ hours from the import zone can fall in the neighbouring week); a weight with `0` reps imports as a 0-rep set and an Android `0.0,0` cardio row with a distance lists as "timed, distance or weight-only" (N4, check on Ben's file); Undo changes session status without a per-session audit entry (the job records the undo; N5); per-answer re-analysis and the SHA-256 run on the JS thread and need timing on the phone (N10, check 27).
- **Still open after review round 3:** the undo alert doesn't yet say that a later import skipped some of these dates (r3 N5: needs a query across other imports' rows); Progress still counts imported workouts as `n workouts logged` (r3 N3, placeholder screen); the dumbbell screen's copy (difference 20) and the catalogue's `implements` values need the designer and catalogue owner.
- **Still open after review round 4:** a one-dumbbell exercise's imported sets still read `70 lb each` after the dumbbell screen said `(one dumbbell)` (r4 N1; how a per-hand load is shown for a one-dumbbell exercise is app-wide, spec issue r4 SP1 for the designer); the undo alert and later imports (r3 N5); the FitNotes default names used in the tests are the review's and the research sample's, not a verified full list (check 16: run Ben's real names through the matcher before he imports); an `Add new` answer for a name whose sets were all skipped saves an alias to an exercise that isn't created, so that name is asked again next time.
- **Open for Ben:** which app and version; kg or lb; whether dumbbell weights are per dumbbell, and how he logged one-arm and goblet exercises (one dumbbell's weight, or something else; review r3); whether barbell weights include the bar and its weight; how assisted pull-ups were logged (negative weights?); whether warm-ups were logged (they'd arrive as working sets); whether comments hold effort ratings; where the workouts were; and the domain decision P-I3.
