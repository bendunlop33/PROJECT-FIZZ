# 0023: Delete my data and Reset coaching knowledge as database file swaps

**Status:** Proposed, 2026-10-11 (developer); revised the same day after reviews `docs/reviews/your-data.md`, `docs/reviews/your-data-r2.md`, `docs/reviews/your-data-r3.md`, `docs/reviews/your-data-r4.md`, `docs/reviews/your-data-r5.md` and `docs/reviews/your-data-r6.md`. Numbered 0022 until review r4 (B2): main's `0022-pre-start-draft.md` landed first, so this ADR is 0023; reviews r1–r3 call it ADR 0022. It follows the spec (§4.5, check 30, check 31a) except for the step order and how `Undo last reset` works (below, both questions for Ben); the earlier divergences are withdrawn. Waiting on Ben for eight items ("For Ben" below; also listed in `docs/brief/CHANGELOG.md` as awaiting Ben): Export JSON-only, the pre-delete safety net, Reset and playbook candidates, the §4.5 step order, Reset and today's edits, the knowledge-only Undo last reset, Reset while Undo last restore is pending, and B12. Stays Proposed until he answers or says "merge as is, follow-up slice" (review r6 S2). Built and tested on Linux (real SQLite through the node driver and the expo-sqlite stand-in); not yet run on the iPhone.

## Context
data-import-export §2.6, §2.7, §3.6 and §4.5 (CLAUDE.md rule 10) ask for `Export: My data / Coaching knowledge only`, `Delete my data (keep coaching knowledge)` and `Reset coaching knowledge`, atomic and resumable after a force-close. The schema's append-only triggers forbid deleting sessions, sets, audits, coach records, memories and playbook candidates inside SQLite (ADR 0005: "deleting data is deleting database files"). Dropping the triggers would need a migration and would weaken the history guarantees for every other write.

## Decision
- **Every table is assigned to a domain** in `packages/persistence/src/data-domains.ts`. `exercises` is split by `owner_id` (no owner: Coaching knowledge; an owner: Your data, the same rule as the restore preview). A test compares the list with `sqlite_master`, so a new table fails until it is classified.
- **Delete** builds a new database file with only the Coaching-knowledge rows, integrity-checks it, and switches the `fizz-meta.db` pointer in one transaction (the restore mechanism). A force-close before the switch leaves all of Ben's data; after it, none. A marker (`data-ops.json`) is written just before the switch and records when the switch happened, so a resume finishes the clean-up but never swaps again (that would delete anything logged since). The clean-up, in order, each step repeatable: the old file and the rollback generation (and the last-restore record; an old file whose earlier removal failed is removed first, never dropped from the slots); **every scheduled workout alert** by its `fizz.rest.` prefix, whether or not this run scheduled it (a resume runs after a relaunch), and delivered ones, failing the step if one is left; **every backup file on this phone** and the backup record (`backup-state.json` started again), then one coaching-knowledge-only backup (`after_delete`); the Your-data files outside SQLite (`coach-connection.json`, `device-prefs.json`, crash notes, damaged copies kept aside, the capability-probe database) and **cached import and restore files**: the app's `tmp` (where iOS's document picker puts its copy of a picked FitNotes CSV or backup, `tmp/<bundle>-Inbox`) and `Library/Caches` are emptied, failing the step if anything is left. The pickers also delete their copy as soon as it is read (review r2 B1). The list lives in `apps/mobile/src/device/personal-files.ts`, which the phone and the test harness share; the ChatGPT sign-in (removed from the phone first, then revoked online, bounded at 10 s, offline is fine) and every Keychain item by key. No backup of Ben's data is made on the phone; the safety net is `Save a copy to Files first`, listed first with `No copy off this phone. Deleting removes the backups on this phone too.` when there is no copy in Files (§3.6).
- **Step order differs from §4.5** (review r3 B1, spec issue 2). §4.5 runs the Keychain, then alerts, then one transaction. The code runs `database` (the swap) first, so a failure before the swap deletes nothing, then `coach_sign_in` (sign-out, bounded online revoke, Keychain wipe), then `alerts`, `backups` and `settings_files`. Credentials stay the first thing after the swap, because Keychain items survive an uninstall. After the swap **every step runs even when an earlier one fails**; the first failure is the one reported, and the marker records every step that failed. One stuck file can't keep the ChatGPT sign-in on the phone.
- **A delete that can't finish at launch** shows `Deleting your data didn't finish`. If the switch never happened, the marker is cleared and the screen says `Nothing was deleted` (Continue opens the app as it was). If it did, the screen says `Your data is removed from the app. Some of it is still on this phone.` and `<step> didn't finish.`, with `Try again`, and `Continue`, which clears the marker and records the step as unfinished, so the app opens at first run and a later launch never retries over new data. If the switch failed and the data couldn't be read to check, it says `Couldn't check whether your data was deleted.` and keeps the marker (review r2 N2).
- **`Finish deleting`** (review r2 S2, r3). After `Continue`, Data & backup shows one warning line, `Deleting didn't finish (<step>). Some of your data is still on this phone.`, with `Finish deleting`. It re-runs only the steps that failed, never the swap, and keeps what Ben made since: backups recorded after `Continue`, the Undo copy of a later restore or reset, and the alert of a workout in progress (every other `fizz.rest.` alert is cancelled). A ChatGPT sign-in or settings set up since `Continue` are removed only if that step itself failed; its confirmation then says `Signs you out of ChatGPT.`. A later complete Delete marks every earlier unfinished delete as done, so the line goes. The app relaunches after it.
- **`tmp` and `Caches`** (review r3 S2; still unverified on the device). `settings_files` deletes everything in both, but only the picker inbox (`tmp/<bundle>-Inbox`) is checked strictly: a picked file left there fails the step. Entries iOS frameworks keep or recreate (URL cache, Metal shader cache) are returned, not treated as a failure, because GymSmarter writes nothing else there itself (they aren't shown anywhere yet). Inside the step every part runs (Documents files, the probe database, then `tmp`/`Caches`) even when an earlier one throws, and the first failure is reported, so a stuck settings file never leaves the picker's copies behind (review r4 N1).
- **Sign-out time limit** (review r4 N4). Both the local sign-out and the online revoke are bounded by the same 10 s; a sign-out that doesn't answer counts as not confirmed online, and the Keychain wipe runs anyway. The wipe itself has no time limit (a hung Keychain call would hold the cover; device check).
- **Reset** builds a new file with every Your-data row, the knowledge exercises Ben's records use, and the bundled starter list. It switches in one transaction and keeps the old file as the rollback generation, recorded as `reset`. **`Undo last reset`** is offered on Data & backup and in the done alert; undoing records `undo_reset`, and undoing that puts the reset back. This needed meta-database migration 3 (the one-row `database_slots` table is rebuilt to widen the `switch_reason` CHECK). Reset is refused while a workout is unfinished (DX4, as Restore and Import; review r2 S3): store writes don't take the manager lock, so a set logged between the snapshot and the switch would be lost, and Undo would be blocked anyway. Reset backs up on the phone first (`before_reset`; it changes no personal data) and never touches credentials.
- **`Undo last reset` is knowledge-only** (review r5 B1, S1; differs from §3.6, which calls it "the same mechanism as Undo restore"). A whole-file swap would revert anything logged since the reset, while the row says it brings back coaching knowledge, and a later Reset would then delete the file holding those workouts. Undo (and redoing it, `Switch back to the reset coaching knowledge`) builds a new file from every Your-data row on the phone now plus the other file's Coaching knowledge (and any knowledge exercise Ben's records use that it lacks), integrity-checks it and switches to it. The file switched away from is kept for the next Undo; the one it replaces was an earlier state of the same data and is dropped. Any unfinished workout blocks it, as it blocks Reset (a set logged during the copy would be lost). Its confirmation says `Your data isn't changed.`
- **Reset and the copy kept for Undo** (review r5 B1, spec issue 2). Reset replaces the rollback generation. Before it, the manager compares that copy with the phone (`domainSummary().keptForUndo`): a copy kept by Reset or its Undo counts only records whose ID is gone from the phone (it's an earlier state of this data); a copy kept by a restore or its Undo counts changed records too, as the restore preview does. When something would be lost, the Reset alert names it (`The copy kept for Undo (since <date>) holds 1 workout that isn't on this phone. Reset saves that copy as a backup on this phone, then deletes it.`), and Reset first saves that copy as an on-phone backup (`kept_for_undo`, kind `manual`, so rotation never deletes it) and then makes the usual `before_reset` backup. If either backup fails, nothing is reset and `Undo last restore` stays. A copy that can't be read can't be saved; the alert says `can't be read. Reset deletes it.` (as the restore preview does). The manager refuses such a Reset (`kept_copy_at_risk`) unless the caller passes `dropKeptCopy`, so no path drops it silently. The stamp covers which file is kept, so the alert Ben saw is the one that applies.
- Both are confirmed against a **stamp** of the current data (rule 5, the restore preview's stamp) and are idempotent by **op ID** (the ledger remembers the last 20). A damaged ledger is kept aside and started again once Ben confirms Delete or Reset; at launch it is left alone.
- **Export** writes one domain as JSON (`format: 'fizz-export'`, JSON columns opened) through the Files folder picker, then reads it back. With nothing in the chosen domain, Export is disabled and shows `Nothing to export`.
- **Pre-start drafts** (main's ADR 0022, migration 7; review r4 B1, S1). `pre_start_drafts` is owner-scoped Your data: exported with My data, removed by Delete, counted on Data & backup, and its swap targets keep their knowledge exercises through Reset. **Reset and `Undo last reset` keep Ben's open draft as it is** (same status and version): a Reset changes no Your-data row, so a Reset that changes nothing with a draft open stays `unchanged`. Only a restore, and undoing a restore, discard open drafts (ADR 0022 §5). Tested at the database and app-service levels.
- No training-schema migration.

## For Ben
- **Export is JSON only in this milestone.** CSV, FitNotes 2 CSV, date ranges, warm-up toggle and the share sheet (§2.6, §4.4) aren't built; the folder picker is used instead. Proposed as a follow-up slice; accept JSON-only for now or ask for it before merge.
- **Pre-delete safety net** (review spec issue 1): the spec relies on `Save a copy to Files first`, listed first when there is no copy off the phone. Is that enough, or should Delete ask "No copy off this phone. Save one first?" before the alert?
- **Reset and playbook candidates** (spec issue 2): the schema has only `to_review` and `withdrawn`, so Reset deletes every candidate (the list says `N rules to review removed`). The spec's "approved and rejected go back to To review" needs approval to ship first.
- **Step order** (review r3 spec issue 2): database first, then credentials, unlike §4.5's Keychain-first order. If accepted, §4.5 should say so and require credentials to be the first step after the swap.
- **Reset and today's edits** (review r4 spec issue 1): the specs say only that a restore discards open drafts. The code keeps them through Reset and its Undo (above). Confirm, and the overview and data specs should say so.
- **Undo last reset, knowledge-only** (review r5 spec issue 1): §3.6 says it's the restore mechanism (a whole-file swap). The code restores only Coaching knowledge and keeps everything logged since (above). Confirm; §3.6 should then say so.
- **Reset with a copy kept for Undo restore** (review r5 spec issue 2): §3.6 doesn't say what Reset does to `Undo last restore`. The code replaces it and, when the copy holds data that isn't on the phone, names it in the alert and saves it as a backup first (above). Alternatives: refuse Reset until the restore is settled, or keep `Undo last restore` and offer no `Undo last reset`. Confirm or pick one.
- **Custom exercises and aliases** (spec issue 3, B12): the code treats owned exercises and `exercise_aliases` as Your data, matching the restore preview; the spec calls them Coaching knowledge.

## Consequences
- Delete and Reset copy the whole database once (about 1.2 MB per 300 workouts, ADR 0005). Time on the phone is to be measured.
- Custom exercises (an owner) are deleted with Your data and untouched by Reset. Open decision B12 would make them Coaching knowledge; this is a one-line change in `domainOf`.
- **Not built:** CSV and FitNotes 2 CSV export, export ranges, the iOS share sheet (export uses the folder picker), guide files and the guide index (not in the app yet), saved import layouts (no table yet; the import's `exercise_aliases` are Your data and deleted), cancelling AlarmKit alarms and Live Activities and stopping audio (not wired yet; only the rest notification is cancelled; add them to the clean-up when they land), releasing a backup-folder bookmark (not stored yet), a write gate while the manager switches files (review N6: a write that reaches the old file between the snapshot and the switch is lost, as with restore; the cover is modal).
- **Device checks:** Keychain items gone after Delete (including after a reinstall), `deleteDatabaseAsync` removes `-wal`/`-shm` for the old files, `Documents/backups` empty except the knowledge-only backup, the probe database gone, a force-close during the cover finishes on relaunch, and the folder-picker export to iCloud Drive. Also: the picker's copy is deleted after an import, a restore and a Check a backup (expo-file-system allows writes outside Documents/Caches only where iOS reports the path writable); `tmp` and `Caches` empty after Delete, and which entries iOS keeps or recreates there (they are reported, not failed, so the check is whether any can hold Ben's data, such as an NSURLCache copy of a coach reply); the app-switcher snapshot (iOS 17+ keeps it in `Library/SplashBoard`, which Delete doesn't touch; it can show Ben's last screen until the next backgrounding; review r3 N4); a pending rest alert cancelled by a delete finished at launch; and the first-run status card when the `after_delete` backup fails (review r2 N5).
